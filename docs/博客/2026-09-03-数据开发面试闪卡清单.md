## 分支一：OneData 与总线矩阵（9张）

### 卡1 总线架构怎么设计的？
**A**：骨架句「**业务过程 × 一致性维度 = 交点**」——行是业务过程，列是一致性维度。三步走：①划分数据域、确立业务过程 ②确定公共一致性维度和度量 ③判断业务过程与维度的关联。
**追问**：能举个 case 吗？→ 订单域交易成功：行拆成下单/支付/发货/确认发货，列是商品/品牌/类目 + 城市/金额。

### 卡2 为什么用业务划分主题域而不是其他方式？
**A**：数字钩子「**3 种划分：部门 / 系统 / 业务**」。没跨部门数据→排除部门划分；系统划分适合传统数仓（电信、证券，系统稳定耦合低）；我们选**业务划分**：抽象核心实体（用户/商品/订单）+ 动作（浏览/下单/退款）→ 组合成用户域、商品域、订单域。

### 卡3 一致性维度表是什么？
**A**：不同事实表**共享同一套维度表**，统一定义 + 唯一主键。收益三连：准确性 ↑、复用性 ↑、开发维护成本 ↓。
**追问**：本质是什么？→ 提供**统一的业务视角**。

### 卡4 一致性事实表是什么？
**A**：消除指标歧义——**一个指标一个口径**。例：销售额算不算运费、扣不扣退款，先定唯一口径，派生指标在此基础上再算。

### 卡5 OneData 是什么？三个 One 是什么？
**A**：阿里方法论，目标「统一、规范、可共享」。数字钩子「**3 个 One**」：
- OneModel 模型统一（分层、数据域、总线矩阵）
- OneID 实体统一（核心实体跨系统唯一标识）
- OneService 服务统一（统一数据出口/接口）

### 卡6 Kimball 和范式模型的区别？
**A**：对比句「**业务驱动 vs 数据驱动**」。Kimball：快速构建集市、高效交付，事实表+维度表，星型/雪花。范式模型：企业级全局设计、避免冗余、周期长。
**追问**：维度建模四步流程？→ **选业务过程 → 声明粒度 → 确定维度 → 确定事实**（「过程-粒度-维度-事实」口诀）。

### 卡7 星型 vs 雪花？
**A**：星型 = 事实表 + **一层**维度表，允许冗余，**空间换时间**，取数高效；雪花 = 维度表再分层，省存储但多层 join 伤查询。
**追问**：case？→ 星型：订单事实表 + 商品/用户维表；雪花：商品维表再延伸行业/类目维表。
**追问**：还有别的模型吗？→ **星系模型**：多事实表共享同一套维度表。

### 卡8 DWS 会跨域吗？
**A**：会。历史原因存在跨域，但主体边界明确；特殊的是**用户、商家这类实体宽表一定会跨域**。

### 卡9 建模三条经验？
**A**：数字钩子「**3 条**」：①高内聚低耦合（业务相近/粒度相同放一起，高概率同时访问的放一起）②公共逻辑下沉 DWS（口径统一）③核心模型与扩展模型分离（高复用字段进核心表，低复用进扩展表）。
**追问**：字段命名呢？→ 同义字段必须同名，用规范定义里的名称。

## 分支二：数仓分层与事实/维度表设计（10张）

### 卡10 数仓四层怎么分工？
**A**：口诀「**贴源 - 明细 - 汇总 - 应用**」：
- ODS 贴源层：同构抽取 ≈ 原始数据 + 技术字段
- DWD 明细层：清洗转换维度退化，按业务过程拆事实表
- DWS 汇总层：轻度汇总（商家×用户、商家×渠道），算人数/客单价
- ADS 应用层：报表展示（转化率、留存、画像）

### 卡11 每层大概多少张表？（老板级追问）
**A**：ODS 100-200 / DWD 约100 / DWS 约150 / ADS 上百-上千 / DIM 约150。主题域 7 个：**用户、行为、商品、广告、订单、触点、商家**。

### 卡12 维度退化是什么？哪些维度适合退化？
**A**：把关键维度属性**直接冗余进事实表**。三类可退化：①高基数（订单编号、发票号）②简单维度（订单状态、优惠券类型）③高复用属性（交易时间戳）。
**追问**：退化力度？→ **DWD 谨慎退化（保原子性一致性），DWS 积极退化（优化查询）**。

### 卡13 维度表怎么建设？
**A**：四步：①识别维度（源表从 ODS 取）②定业务主键（唯一）+ 描述属性 ③维度退化处理 ④缓慢变化维处理（SCD1/2/3）。

### 卡14 缓慢变化维怎么处理？
**A**：数字钩子「**3 招**」：①覆盖（历史数据有错时，如手机号注册错）②**新加一行**（起始/有效时间标记生命周期）③**新加一列**（历史值写进新字段）。

### 卡15 拉链表怎么设计？
**A**：记录生命周期，用起始时间 + 有效时间标记，**开链/闭链**。新数据插入：起始时间=今天、有效时间=无穷大，同时**闭链**历史记录（改其有效时间）。

### 卡16 事实表有哪几种？
**A**：数字钩子「**3 种**」：①事务事实表（每行一个事件）②**周期快照**（记录周期末状态，月表按月产出）③**累计快照**（一行 = 一个业务全生命周期，订单从下单到售后）。

### 卡17 退款周期15天，事实表怎么处理？
**A**：每天增量写 → 用**更宽的时间范围筛选**：退款周期15天就筛过去一个月数据，取状态=退款且退款时间=昨天的，增量写入。

### 卡18 订单全链路明细宽表放哪层？为什么？
**A**：放 **DWD**——只是明细多表关联，没做聚合。
**追问**：为什么不放 DWM？→ 我们为简化层级没设 DWM 层；DWM=粒度不变/轻度聚合+宽表，DWS=高度聚合。
**追问**：字段越来越多怎么办？→ ①核心/扩展模型分离 ②技术上数据湖（Iceberg）。

### 卡19 订单各环节时效怎么算（1号下单/5号支付/10号发货）？
**A**：关键词「**数据回刷**」：先建单事务事实表（下单/支付/发货/收货各一，状态进各自分区）→ 建多事务宽表，**回刷过去30天**，下单表作左表 left join 各状态表取事件时间，写回对应分区。
**追问**：SQL 套路 → `INSERT OVERWRITE ... PARTITION(order_date)` + 多个 LEFT JOIN + CASE WHEN 定位 current_status。

## 分支三：指标体系与数据质量（8张）

### 卡20 OSM 指标体系怎么搭？
**A**：骨架句「**目标 → 策略 → 度量**」。例：O=提升 GMV；S=提单量/提客单价/降退款/提履约；指标分三级：
- 一级（战略）：GMV、订单完成金额
- 二级（策略）：订单数、转化率、客单价、退款率
- 三级（诊断）：分渠道/品类/新老客/地区/时段

### 卡21 UJM 是什么？和 OSM 什么关系？
**A**：UJM=用户旅程地图，以用户为中心描述「接触→兴趣→下单→复购」全路径。关系：**OSM 定宏观目标，UJM 把策略具体化成每个触点的优化点和指标**。
**追问**：UJM 拆解六要素？→ 用户行为/业务目标/接触点/潜在痛点/机会点/衡量指标。

### 卡22 数据一致性怎么保证？
**A**：数字钩子「**3 个层面**」：①**模型层**：统一出入口，公共逻辑下沉 DWS，一致性维度表 ②**平台规范层**：指标管理平台统一口径 + 命名/开发规范 ③**质量层**：表级（量级波动）+ 字段级（空值率、主键唯一）监控 + 交叉验证。

### 卡23 质量监控体系怎么搭？
**A**：按对象分三类监控：**表**（唯一性、量级波动）、**字段**（空值率、数值/枚举范围）、**任务**（重要任务挂基线，报错/延迟即告警）。
**追问**：老板问治理？→ 规范制定 → 内部宣讲 → 事后复盘 → 规避问题。

### 卡24 一条记录=5，怎么判断它是对的？
**A**：数字钩子「**4 重验证**」：①源数据直查 ②质量监控（波动/阈值告警）③**多源交叉验证**（5 个订单↔5 个包裹↔库存扣减）④业务合理性（对比近30天）。

### 卡25 ETL 流程说一下？
**A**：三段式「**抽-转-载**」：抽取（按数据量判断增量/全量，wedata 平台）→ 转换（清洗：去重/完整性/正确性；转换：格式标准化、字段拆合、关联维表、衍生指标）→ 加载（增量/全量）。

### 卡26 怎么评价数仓做得好？
**A**：三个视角：①质量：时效正确、不破基线 ②应用：口径一致、**模型复用率高**（大部分指标 DWS 直接取）③业务：有效赋能、交付效率高、数据资产价值。

### 卡27 大促转化率提升2.5pp 怎么做到的？
**A**：数据赋能路径：打通跨设备 ID（idmapping）→ 用户行为宽表作标签底表 → **三类标签**（统计类：累计消费；规则类：近30天消费>500=高价值流失人群；算法类：流失风险分）→ BI 平台圈人，运营执行。
**追问**：怎么流程化？→ 标签注入资产管理平台，运营拖拉拽组业务流（圈人→发券）一键执行。

## 分支四：Hadoop / Spark / Flink / 数据湖（13张）

### 卡28 Hadoop 三大组件？
**A**：**HDFS + MapReduce + YARN**。HDFS 主从：NameNode 存元数据，DataNode 存数据块，**默认 3 副本**，一次写入多次读取。MapReduce 分而治之。YARN 主从：RM 全局资源，NM 节点资源，AM 申请容器。

### 卡29 MapReduce 流程 + shuffle 做了什么？
**A**：map 阶段：切片→<k,v>→环形缓冲区→溢写磁盘；reduce 拉取同 key 分区处理再外写。
Shuffle 六步（数字钩子 **map3 + reduce3**）：map 侧 ①分区（hash%Reduce数）②排序溢写 ③归并合并；reduce 侧 ①拷贝 ②归并 ③输入计算。

### 卡30 MapReduce 框架优势？
**A**：数字钩子「**3 条**」：①数据本地性（移动计算不移动数据）②容错（任务失败换节点重启）③并行海量数据。

### 卡31 Spark 提交后的执行流程？
**A**：四步链：**惰性记录 RDD 依赖 → 生成 DAG 逻辑计划 → DAGScheduler 按宽依赖切 stage → TaskScheduler 分发 task 给 executor 线程池执行**。
**追问**：宽窄依赖？→ 宽：一父对多子（groupByKey/reduceByKey）需 shuffle；窄：一对一（map/filter）无需 shuffle。

### 卡32 Spark SQL 执行过程？
**A**：两计划：①Catalyst 解析 SQL→逻辑计划：未解析→Catalog 绑定元数据→优化（**谓词下推、列值剪裁**）②逻辑计划→物理计划，**Tungsten 生成字节码**→转 RDD 集群执行。

### 卡33 Spark 相对 MapReduce 的优势？（重点题）
**A**：数字钩子「**5 条，前3是重点**」：①基于内存计算 vs 磁盘 IO ②DAG 执行引擎 vs 固定两阶段 ③Lineage 血缘容错（只重算丢失分区）④多线程 vs 多进程（省 JVM 启动）⑤shuffle 非必要不排序。

### 卡34 RDD 怎么理解？
**A**：弹性分布式数据集，三个切面：①**依赖**：宽窄依赖划分 stage ②**容错**：血缘重算，不从头回溯 ③**操作**：转换算子（map/filter/join，惰性）+ 行动算子（count/collect，触发计算）。

### 卡35 数据倾斜怎么优化？（必考）
**A**：三类原因对应三板斧：
- **聚合倾斜** → 两阶段聚合+加盐打散（先加盐局部聚合，再去盐全局聚合）
- **join 倾斜** → 大表小表：广播小表 / 热点 key 分离加盐（两表都加）；大表大表：**分桶表+分桶 join** 免 shuffle
- **空值倾斜** → 随机值替换 / 分离处理（null 单独 UNION ALL）
**追问**：Spark3 捷径？→ 开 AQE 自适应查询执行。
**追问**：真实 case？→ 个别 task 慢+Spark UI 判断→group by 查量级发现某表百万级 vs 常态几千→清历史数据。

### 卡36 系统优化整体框架？
**A**：三分类「**参数 / 倾斜 / SQL**」；想不起来就说流程：读取阶段（分区列剪裁）→ 计算阶段（聚合加盐、join 优化、with 替子查询）。
参数优化四点：executor 核数内存、shuffle 分区数（默认200，瓶颈在内存适当调大）、AQE、小文件自动合并。

### 卡37 Spark shuffle 有哪几种？默认是哪个？
**A**：演进线「**Hash → 合并 Hash → Sort**」：M×R 文件爆炸 → Core×R 仍多 → 默认 Sort Shuffle（2×M：1 数据文件+1 索引）。
Sort 内部 **3 种写入器**按条件自动选：①Bypass（无聚合+分区≤200）②Unsafe（无聚合+序列化支持重定位+分区≤2²⁴，二进制排序省内存）③SortShuffle（通用，内存→溢写，key 排序）。

### 卡38 小文件过多危害与治理？
**A**：三大危害：①NameNode 元数据内存耗尽 ②海量 task 调度开销>计算时间 ③资源利用率低、吞吐下降。
治理：**事前** repartition/coalesce 控制写入数量；**事后**定期合并。
**追问**：OOM？→ 分 driver（collect 操作/加大内存）和 executor（合理分区数/加大内存/调比例）。

### 卡39 reduceByKey vs groupByKey？
**A**：一句话「**先本地聚合，再 shuffle**」——groupByKey 全量走网络，性能差；reduceByKey 节点内先聚，大幅减少 shuffle 量。

### 卡40 Flink 关键特性（4个）+ 数据湖/湖仓一体？
**A**：Flink：主从（JobManager 调度/checkpoint，TaskManager 计算），数字钩子「**4 特性**」：①时间语义（事件/处理/摄入时间，处理乱序）②水位线（事件时间进度标记，决定窗口触发）③状态管理（内存/RocksDB）④checkpoint（定期异步快照→HDFS，精准一次）。
湖：原始格式全量存储，**Schema-on-Read**，灵活但治理难。湖仓一体三优势：**事务支持（ACID）、开放格式（Parquet/Iceberg）、流批统一**。
**追问**：UDF 写过吗？→ spark sql 的 udf；例：getLastMonthDays（上月天数）、getUpdateCycle（按分区长度判断更新周期）。

## 分支五：SQL 题型套路（8张）

### 卡41 三个排名函数的区别？
**A**：数据 a,b,b,c,c 的排序结果：**ROW_NUMBER=1,2,3,4,5（不并列）；DENSE_RANK=1,2,2,3,3（并列不跳号）；RANK=1,2,2,4,4（并列跳号）**。
**追问**：还有哪些窗口函数？→ lead/lag over、sum/count/avg/max/min over。

### 卡42 分区 vs 分桶？
**A**：分区=HDFS **目录**，分桶=目录里的**文件**；没分桶要扫全目录，有分桶直接定位对应文件。分桶函数：ntile over、hash。场景：①大表 join 按 key 分桶，同 key 落同号桶免 shuffle ②高效随机抽样。

### 卡43 行转列 / 列转行？
**A**：行转列 = **max(case when subject='数学' then score end) + group by 学生**；列转行 = 多段 union all，每段固定 subject 字面量。

### 卡44 中位数怎么求？
**A**：两法：①row_number 排名 + count(*) over 总数，**取 rnk in (floor((n+1)/2), ceil((n+1)/2))** 再 avg ②percentile_approx(salary, 0.5) 近似。

### 卡45 最大在线人数（直播间）？
**A**：套路「**enter=+1，leave=-1，按时间累计求和取 max**」：先 group by 时间点算净值 flag，再 sum(flag) over(order by time) 得在线曲线，取 max。

### 卡46 最大连续登录天数？
**A**：核心套路「**日期减排名 = 连续组号**」：`date_sub(login_date, row_number() over(partition by uid order by date))` 相同即为同一段连续 → group by 组号 count → max。
**追问**：间隔1天也算连续？→ 改用 lag + **date_diff ≤ 2 打标**，sum(flag) over 生成组号。
**追问**：连续登录月？→ 先按 yyyy-MM 去重取月首日，再用 `date_sub(月首日, interval rnk month)` 分组。

### 卡47 双向好友对数？
**A**：两法：①自 join 反转匹配 + `where f1.user1 < f1.user2` 防重复计数 ②把每对按小大归一 `IF(u1<u2,u1,u2)` group by 后 **having count(*)>1** 即双向。

### 卡48 留存率 / TopN / 连续3次 / 波峰波谷？
**A**：四个高频题一套思路：
- **留存**：min(event_date)=注册日 → date_add(register, n)=event_date 打标 → 人数比值
- **TopN**：row_number over(partition by 部门 order by 薪资 desc) ≤ N
- **连续3次**：`id - row_number() over(partition by num)` 分组 having count≥3
- **波峰波谷**：lag/lead 取前后价，case when 双向比较

## 分支六：Doris 与叙事题（7张）

### 卡49 Doris 整体架构？
**A**：**FE + BE** 两类节点。FE（Frontend）：负责元数据管理、查询解析、查询规划、集群管理，类似「大脑」；BE（Backend）：负责数据存储和查询执行，类似「肌肉」。元数据用 **BDB JE（类 Paxos 多数派）** 保证一致性。

### 卡50 Doris 为什么快？（MPP 关键词）
**A**：数字钩子「**3 个快**」：①**MPP 架构**：多节点并行执行，一份数据多副本分摊查询 ②**列存 + 前缀索引**：按列存储压缩率高，前缀索引（有序稀疏索引）加速过滤 ③**预聚合模型**：建表即选定聚合方式，查询直接读结果。

### 卡51 Doris 三种数据模型？
**A**：①**Duplicate**：不去重，存明细 ②**Aggregate**：建表时指定聚合（SUM/MAX/MIN/REPLACE），导入时预聚合 ③**Unique**：主键唯一，REPLACE 语义实现更新。选型口诀「**明细用 Duplicate、报表用 Aggregate、更新用 Unique**」。

### 卡52 Doris 分区分桶怎么设计？
**A**：两层：**分区（Partition）按时间/范围切**，利于裁剪和冷热分离；**分桶（Bucket）按高基数 join key 哈希**，桶数经验值 = BE 数 × 其核数左右，单桶数据量 1-10G 为佳。

### 卡53 Doris 和 Hive 系数仓怎么分工？
**A**：**Hive/Spark 管离线批量加工**（T+1 大规模 ETL），**Doris 管交互式查询和高并发报表**（亚秒级响应）。常用链路：DWD/DWS 结果通过 Broker Load / 例行导入进入 Doris，对外服务查询。关键词「**湖仓加工、MPP 服务**」。

### 卡54 项目叙事框架（讲最好的项目）？
**A**：数字钩子「**基建10个月 + 质量2-3个月**」：①调研 1-2 月：数据域、分层、命名规范 ②建设：ODS 1-2 / DWD 2-3 / DWS 2-3 / ADS 1-2 月 ③质量规则+告警+报表 2-3 月；之后日常需求迭代。
**追问**：难点？→ 指标不一致（模型/规范/监控三层解）、数据质量差（质量监控+交叉验证）。想不起就说「复杂业务怎么抽象建模」。

### 卡55 开放题三板斧？
**A**：①**棘手问题**：口径对不齐被投诉 → 解法：统一机制平台 + 公共逻辑下沉 DWS ②**职业发展**：内部基建 → 数据理解 → 赋能业务价值 / 结合 AI 做数据 ③**数仓未来**：AI 三方向——开发提效（补全纠错）、智能答疑（知识库扫描）、ChatBI 智能体（说需求即出数）。
